## 1) What is implemented now

This project is a local AI support copilot with:

- FastAPI backend for tickets, drafts, knowledge ingest, and memory endpoints
- Streamlit dashboard for support workflow
- SQLite for ticket/draft/customer state
- ChromaDB-backed RAG for static KB retrieval
- Mem0-backed customer memory for cross-ticket continuity
- LangChain + Groq LLM orchestration with tool-calling
- Structured draft context (`context_used`, version `2`) rendered in UI

It supports full flow:

1. Ingest KB
2. Create ticket
3. Generate draft (manual or auto)
4. Accept/discard draft
5. Query customer memory (memory probe)

## 2) Runtime architecture (current)

### Entry points

- Backend runtime entrypoint (compat wrapper): `main.py`
- Backend primary app factory: `customer_support_agent/api/app_factory.py`
- Dashboard: `app.py`

### Core orchestration

- `customer_support_agent/services/copilot_service.py` (`SupportCopilot`)
  - Pulls memory hits (Mem0)
  - Pulls KB hits (RAG/Chroma)
  - Invokes LLM with tools
  - Executes tool-call loop (up to 4 rounds)
  - Forces fallback synthesis if tool-call run returns empty text
  - Returns draft + structured context payload

### Infra modules

- `customer_support_agent/repositories/sqlite/*`: SQLite schema + repositories
- `customer_support_agent/integrations/memory/mem0_store.py`: Mem0 wrapper + noop fallback
- `customer_support_agent/integrations/rag/chroma_kb.py`: KB ingest/query using Chroma
- `customer_support_agent/integrations/tools/support_tools.py`: mocked billing/plan/load lookup tools
- `customer_support_agent/core/settings.py`: env-backed settings and path resolution
- `customer_support_agent/schemas/api.py`: API request/response schemas
- `customer_support_agent/api/routers/*`: domain routers
- `customer_support_agent/api/dependencies.py`: DI providers
- `customer_support_agent/services/draft_service.py`: draft persistence/serialization workflow
- `customer_support_agent/services/knowledge_service.py`: knowledge ingest facade

Compatibility wrappers preserved at repo root:

- `config.py`, `models.py`, `rag.py`, `memory.py`, `tools.py`, `database.py`, `copilot.py`, `main.py`

## 3) Data model (SQLite)

Database file: `data/support.db`

Tables:

- `customers`
  - `id`, `email` (unique), `name`, `company`, `created_at`
- `tickets`
  - `id`, `customer_id`, `subject`, `description`, `status`, `priority`, `created_at`, `updated_at`
- `drafts`
  - `id`, `ticket_id`, `content`, `context_used` (JSON string), `status`, `created_at`

Important behavior:

- Accepting a draft sets ticket status to `resolved`.
- Draft statuses used in practice: `pending`, `accepted`, `discarded`, `failed`.

## 4) API contract map

Implemented routes in `customer_support_agent/api/routers/*` and registered by `customer_support_agent/api/app_factory.py`:

- `GET /health`
- `POST /api/tickets`
- `GET /api/tickets`
- `GET /api/tickets/{ticket_id}`
- `POST /api/tickets/{ticket_id}/generate-draft`
- `GET /api/drafts/{ticket_id}`
- `PATCH /api/drafts/{draft_id}`
- `POST /api/knowledge/ingest`
- `GET /api/customers/{customer_id}/memories`
- `GET /api/customers/{customer_id}/memory-search`

### Key request schemas

- `POST /api/tickets` (`TicketCreateRequest`)
  - Required: `customer_email`, `subject` (min 3), `description` (min 10)
  - Optional: `customer_name`, `customer_company`
  - `priority`: `low|medium|high|urgent`
  - `auto_generate`: default `true`

- `PATCH /api/drafts/{draft_id}` (`DraftUpdateRequest`)
  - `content`: optional text
  - `status`: `pending|accepted|discarded`

- `POST /api/knowledge/ingest` (`KnowledgeIngestRequest`)
  - `clear_existing`: bool (default `false`)

### Draft generation behavior

- Manual generate: `POST /api/tickets/{id}/generate-draft`
- Auto-generate on ticket create when `auto_generate=true` using FastAPI `BackgroundTasks`
- If draft text is empty, API writes fallback non-empty text and appends error in `context_used.errors`
- If copilot fails in background path, draft is created as `status="failed"` with structured error context

## 5) Structured context payload (`context_used`)

`version: 2` payload generated by `SupportCopilot._build_context(...)`:

- `ticket`: `{id, subject, priority, status}`
- `customer`: `{id, email, name, company}`
- `signals`:
  - `memory_hit_count`
  - `knowledge_hit_count`
  - `tool_call_count`
  - `tool_error_count`
  - `knowledge_sources`
- `highlights`:
  - top memory snippets
  - top KB snippets
  - top tool summaries
- `memory_hits`: raw normalized Mem0 hits
- `knowledge_hits`: raw KB hits
- `tool_calls`: trace entries with:
  - `tool_name`, `tool_call_id`, `arguments`
  - `status` (`ok|error|skipped`)
  - `summary`, `output`, `output_text`
- `errors`: optional list (memory disabled, empty-response fallback, etc.)

UI renders this in `app.py` under `Context used` expander with metrics + table + per-tool details.

## 6) Memory vs RAG in this implementation

### RAG (`customer_support_agent/integrations/rag/chroma_kb.py`)

- Source dir: `knowledge_base/` (`*.md`, `*.txt`)
- Chunking: `RecursiveCharacterTextSplitter`
  - `chunk_size=800`
  - `chunk_overlap=120`
- Storage: Chroma persistent collection `support_kb` at `data/chroma_rag`
- Query output fields: `content`, `source`, `distance`

### Memory (`customer_support_agent/integrations/memory/mem0_store.py`)

- Store: Mem0 with Chroma vector store at `data/chroma_mem0`
- LLM provider in Mem0 config: `groq`
- Embedder selection:
  - `gemini` if `GOOGLE_API_KEY` exists
  - else `openai` if `OPENAI_API_KEY` exists
  - else `huggingface` model `all-MiniLM-L6-v2`

### Memory update semantics

- Memory is written only on **accepted draft** (`PATCH /api/drafts/{id}` with `status=accepted`)
- `save_accepted_resolution(...)` stores user/assistant message pair via `add_resolution(...)`
- Accepted resolutions are written to two scopes:
  - contact scope: `customer_email`
  - company scope: `company::<normalized-company>`
- Entity-link extraction adds tags like:
  - `endpoint:/v1/orders`
  - `http_status:429`
  - `region:EU`
  - `integration:shopify`
  - `plan:pro`
  - `billing_risk:high`

### Memory retrieval

- During draft generation, memory is searched across both scopes (`customer_email` + company scope) and deduplicated.
- Explicit probe endpoint: `GET /api/customers/{id}/memory-search?query=...&limit=...`

## 7) Tools (current behavior)

Defined in `customer_support_agent/integrations/tools/support_tools.py`, exposed via LangChain tool-calling:

- `lookup_customer_plan(customer_email)`
- `lookup_billing_status(customer_email)`
- `lookup_open_ticket_load(customer_email)`

All three currently return mocked deterministic JSON (hashed by email) and are not calling external billing/CRM systems yet.

`lookup_open_ticket_load` does read real open-ticket counts from local SQLite.

## 8) Streamlit workflow mapping

UI file: `app.py`

- Sidebar:
  - `Ingest Knowledge Base` -> `POST /api/knowledge/ingest`
- Ticket creation form:
  - `Create Ticket` -> `POST /api/tickets`
- Ticket panel:
  - `Generate Draft` -> `POST /api/tickets/{id}/generate-draft`
  - Draft editor bound to latest draft content
  - `Accept Draft` -> `PATCH /api/drafts/{id}` status `accepted`
  - `Discard Draft` -> `PATCH /api/drafts/{id}` status `discarded`
  - `Context used` expander renders structured context
  - `Memory Probe` -> `GET /api/customers/{id}/memory-search`

Error rendering:

- API validation details (`422`) are parsed and surfaced in UI.

## 11) Known limitations / technical debt

- No authn/authz yet (all endpoints open).
- BackgroundTasks are in-process only (not durable like Celery/queue workers).
- Tool outputs are mocked and deterministic, not real integrations.
- First-time Mem0/HuggingFace embedding load can be slow.
- Streamlit logs show deprecation warnings for `use_container_width`; migration to `width=` is pending.
- No migration framework for SQLite schema versioning yet.
